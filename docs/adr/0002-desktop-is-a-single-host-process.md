# 桌面版是**单宿主进程**：后端与所有窗口同属一个进程

2026-10-11 的架构审查（R06/R07）指出：多窗口那边没有契约。改前的实际行为是
"每个启动都是一个独立进程，第二个进程复用第一个的 HTTP"，于是：

* 关掉第一个窗口 → 它的 backend 跟着走（`run_window_first` 的 finally）→ 第二个窗口
  还开着却断网；
* 在第二个窗口点「重启以完成替换」→ HTTP 打到第一个进程，执行的是**它的**退出钩子
  → 用户看到"另一个窗口没了"，而不是自己那个重启；
* 整包替换只等服务器那个 PID，别的窗口还可能锁着同一份安装目录；
* "复用已有实例"的判据是 `/api/health` 返回 200 —— 端口恰好被别的程序占着时会把它
  当成本产品的后端。

## 决定

**第一个启动的进程是宿主**：它拿到 `data_root()/instance/host.lock` 上的独占文件锁，
拥有 backend 与**所有**窗口。后来者：

1. 拿不到锁 → 读 `host.json`（宿主名片）→ 用 `/api/desktop/handshake` 握手
   （产品标记 + 协议版本 + 宿主 pid + 实例 id 四项全对）；
2. 握手通过 → 把"再开一个窗口"写进 `instance/window-request-*.json`（宿主消费掉这个
   文件 = 收下了请求）→ 自己退出，**不建 backend、不建窗口**；
3. 握手不通过（端口被别人占着、或对方不是本应用）→ 如实报错退出，**不猜**。

配套：端口语义拆开 —— 不给 `--port` 时"优先 8765、被占就换空闲"；**显式给了**
`--port` 就是它，被占直接报错（不静默换到别的端口，让用户以为自己在 8765 上）。

## Status

accepted（2026-10-11）

## Consequences

- backend 的生命周期跟着**宿主进程**，不再跟"哪个窗口先关"走：关掉任意窗口都不影响
  别的窗口；所有窗口关掉 → GUI 循环结束 → 宿主退出时收掉 backend（并把名片删掉）。
- 更新重启只有一个执行者（宿主），与 ADR-0003 的"唯一助手"是同一条链。
- 令牌不再需要跨进程传递（"第二个窗口拿第一个进程的令牌"那条路基本废弃）：
  窗口都由宿主开，令牌天然在同一个进程里。
- 用户可见的行为变化：**第二次双击图标不再新开一个进程**，而是让已经在跑的那个再开
  一个窗口；多开的总数仍是"一个后端 + N 个窗口"。
- 多窗口里的缩放、状态这些都落在同一个进程（`native_zoom` 早就是按窗口各自处理的），
  比以前"跨进程操作别的窗口控件"更直接。

真机验证：多窗口是由宿主进程 `webview.create_window` 开的（GUI 线程），
`scripts/` 里没有自动化覆盖 —— 这条要在 Windows 上手动点两次图标确认（见 PR 说明）。

## 什么时候该重开

- 需要"每个窗口独立后端"的产品形态（例如以后要做多用户/多机）；
- 或者 pywebview 在某个后端上不支持"循环跑起来之后再建窗口"（那时退化成
  "第二个启动提示用户用第一个窗口"，但**仍然**不许复用别人的 HTTP）。
