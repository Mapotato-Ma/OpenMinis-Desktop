# 提示前缀必须逐字节稳定（每轮会变的东西一律不进系统提示）

2026-10-11：用户报「这个内核对应的 iPhone 版本缓存命中率不高」。定位下来不是服务商
的问题，是**我们自己每轮都在改前缀**。

## 问题

提示缓存只认最长公共前缀：

* Anthropic 用 ``cache_control`` 标 4 个断点（最后一个 tool、system 块、最近两个
  user turn），命中就是命中那个断点之前的全部内容；
* OpenAI / DeepSeek / 七牛 / OpenRouter 那类自动前缀缓存，比的是请求序列化之后的
  最长公共前缀（工具 schema + system + messages）。

而改前 ``identity_system_prompt()`` 里有 ``current_time_block()``：

    【当前时间】现在是 2026-10-11 21:30（周六，北京时间）

它在 persona 之后、所有纪律与技能清单之前 —— 于是**每 60 秒前缀就变一次**：跨过一分钟
的下一轮，Anthropic 那边 system 断点与它后面的消息断点一起失效（全量重写，还按 1.25×
计费），OpenAI 那边的公共前缀在 ``system`` 处断掉、整段历史按未命中计费。同一分钟内
连着问、以及一轮里工具循环的多次往返仍然命中 —— 这正是"命中率不高但也不是零"的形状。

次要的一条：群成员块由客户端**每轮现传**（``msg["participants"]``），改前拼在系统提示
**末尾**。系统提示一变，后面的消息断点也跟着失效。

## 决定

1. **系统提示只由设置决定**，里面只放天粒度的日期（``current_date_block()``）——
   跨午夜会变一次，可接受；分钟级的时间、群成员这类每轮都会变的东西一律不放进去。
2. 它们改走「**每轮注记**」：由 ``turn_note_block()`` 生成，拼在**本轮用户消息的尾部**，
   并**随消息落库**（``chat_store.TURN_NOTE_MARK``）。放尾部意味着它是"新内容"，前面的
   前缀该命中的照样命中；落库意味着下一轮重建历史时拿到的是**同一串字节** —— 这是命中
   的前提，也是为什么不能只拼给模型、不落库。
3. 展示层（``chat_store.strip_turn_notes``）在界面、会话标题、导出上剥掉这段注记；模型
   上下文保留原样。用户看到的永远是他自己打的那句话。
4. Anthropic 的 1 小时 TTL 接通（provider 配置 ``promptCacheTtl``，默认 ``1h``，可切
   ``5m``）—— 改前 ``enhanced_cache`` 硬编码为 ``False`` 且没有任何入口，用户慢慢打字
   超过 5 分钟，缓存就自然过期。
5. 附件清单的 ``modified`` 改用文件真实 mtime（原来写的是"组装这段 XML 的时刻"）。

## Status

accepted（2026-10-11）

## Consequences

- 判据不再是"感觉"，而是 ``/api/usage`` 已经算好的 ``cacheHitRate`` —— 桌面用量面板
  现在把它显示出来。改完拿同一个服务商连问两轮即可自证。
- 落库的用户消息尾部多了一段机器文本（有固定标记）。凡是**读用户消息做展示**的地方都要
  走 ``strip_turn_notes``（界面、标题已接；将来加导出/搜索要注意）。
- 系统提示与历史前缀从此与时钟无关：同一个会话里连续两轮的请求只有最后一条消息不同。
- 模型上下文里保留的历史注记会带着"当时的时间"，那是事实，不是噪音。

## 什么时候该重开

- 服务商推出"传一个时间参数而不是写进提示"的正式接口（那样连注记都不需要）；
- 或者我们要支持前缀无关的缓存（例如按内容寻址的 long-context cache）。
