# 一次更新 = 一个事务；不为 v0.5.0 保留兼容窗口

2026-10-11 的架构审查（19 项）里，更新那条线占了 5 项（R01–R05），而且全部指向同一个
形状的问题：**更新的每一步散在各调用点，没有唯一的拥有者**。落地时定了两件事。

## 决定一：更新是一个事务（`desktop/update_transaction.py`）

一个 job id + 一个状态机 + 一份不可变快照，进程内单飞、跨进程以落盘的
`updates/txn.json` 为权威：

    idle → checking → downloading → staged → committing → done
                                      │           │
                                      │           └── 退出后由助手接力（唯一一个助手）
                                      ├── manual（源码运行等"只能手动"的情形）
                                      └── failed

三条不变量：

1. **准备 ≠ 提交。** `run()` 只下载 / 解压 / 校验 / 写 journal，绝不 spawn 助手；
   只有用户点「重启并完成替换」（`commit()`）才起那唯一一个助手。改前是"下载解压完
   就把助手叫起来等当前进程 90 秒"，而界面还在让用户慢慢决定 —— 超时后助手自删，
   界面却还说"重启即完成替换"（R02）。
2. **旧版本保留到新版确认启动。** 新版进程在后端健康后写 `updates/boot-ok.json`，
   助手等到它才删 `.old-*`；等不到就原样留着并写进日志与 `state.json`（R04）。
   发出 `start` 不算证据。
3. **破坏性动作只碰本次事务的目录。** 每个删除 / 改名之前过 `assert_owned()`：
   R01 那个"把安装目录的父目录当清理目录"的形态从此不可能发生；平铺整包（没有顶层
   目录）直接拒绝，因为那条路上"哪一层才是安装目录"只能靠猜。

载荷更新也改成"退出后再切"（R05）：活进程里换载荷会让新旧代码混在一个解释器里。

## 决定二：不为 v0.5.0 保留兼容窗口

v0.5.0 已经在用户手上，而它那条整包自动更新链路本身带着 R02/R03/R04。让新版本继续
伺候旧壳的升级路径，意味着**在要修的那段代码里再留一条分支**去复现旧行为 —— 修的东西
和保的东西互相抵消。

所以：发一版新的，发布说明写清"旧版请手动下载一次整包"；从此以后自动更新走新链路。
判断依据是更新清单里的 **shellId**（壳源码指纹）—— 修过壳之后它必然变化，旧版会走
整包分支。因为不承诺旧版的自动升级，实现里**没有**任何版本探测/兼容分支。

## Status

accepted（2026-10-11）

## Consequences

- 更新相关的状态只在 `update_transaction.py` 与三个 HTTP 端点（`/api/desktop/update`、
  `.../status`、`.../restart`）里流动；`ui_mount` 不再持有一份全局状态字典。
- 真机演练（`scripts/update_drill.py`）成为这条链路的常规验证手段：单元测试只能断言
  "脚本里写了哪几行"，而助手脚本的两个已知坑（`timeout /t` 在无控制台时等不了、
  `del "%~f0"` 会让退出码变 1）都只有在真跑 `cmd` 时才看得见。
- 用户侧可见的行为变化：更新分两步（先下载校验、再点重启），且界面会同时显示"正在跑的
  版本"与"待启用的版本"。
- 过期的旧安装目录不再由"下一个版本顺便清"以外的方式处理：`recover()` 只在新版确认
  启动后才删 `.old-*`；没确认时保留并告诉用户它在哪。

## 什么时候该重开

- 真要支持"从某个旧版本自动升上来"时 —— 那需要先定义清楚旧版的行为契约，而不是在这里
  加 if；
- 或者 Windows 之外的平台成为发布目标（现在助手脚本只对 Windows 写，非 Windows 只返回
  脚本路径、不 spawn）。
