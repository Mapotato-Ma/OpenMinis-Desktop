# 桌面界面（无框架那份）才是产品的脸，上游移动端 UI 不是

仓库里同时存在两份前端，规模差 5 倍，都能被内核服务：`web/desktop/`（纯 HTML/CSS/JS，3.9k 行，
无构建步骤，挂在 `/_desktop/`，而且 `/` 会 307 到它）和 `web/src` + `web/dist`
（上游的 React 移动端界面，19.7k 行，由内核的 SPA 兜底路由服务，也会被打进 exe）。

**我们的决定：桌面版的界面工作一律进 `web/desktop/`；`web/dist` 的定位是「上游参考 + 离线兜底」，
不是产品界面。** 理由是这份取舍的三条依据：

1. **桌面要的不是移动端形态。** 上游 UI 是给手机屏幕设计的（底部导航、单列信息流），
   放在 1440×900 的窗口里要重做布局——那已经等于重写。
2. **构建步骤不稳定，接口才稳定。** `web/desktop/` 直接对着内核的 REST/WS 契约写，
   改一行刷新就能看到；而引入 Vite 构建意味着「改界面」要先装 node_modules、
   过一遍构建、再想打包时前端算数据还是算代码。
3. **打包更简单。** 无构建步骤的前端在 PyInstaller 里就是一组数据文件
   （见 `packaging/OpenMinisDesktop.spec` 的注释），不会被构建产物与源码的时序问题咬到。

## Status

accepted（2026-09-27）

## Consequences

- **协议要改时，影响面是 `web/desktop/` 一处。** 它**不**引用上游的 `web/src/api.ts`
  （这是有意的：接口稳定，构建步骤不稳定）。代价是上游 UI 的接口封装若变了，
  我们不会自动受益，得自己跟。
- **`web/dist` 仍在仓库里、仍被打包、仍能被访问。** 这是刻意的：它让「上游界面跑起来是什么样」
  随时可看，也给了「桌面界面产物丢了」时的退路（`attach()` 会在产物缺失时如实汇报
  `uiActive: false`）。但**不要往它上面加功能**。
- 若哪天要复用上游 UI 的成熟组件（例如某个复杂面板），先回来重开这条决定，
  而不是让两份界面各长一半。

## 什么时候该重开

- 上游 UI 变成响应式、能直接用在桌面窗口里；
- 或者桌面界面的维护成本明显超过「复用上游 + 改布局」；
- 或者有第二个需要同一套界面的平台（那时才值得为共享组件引入构建步骤）。
