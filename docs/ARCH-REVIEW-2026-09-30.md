# 架构检查（撇开项目自己的规矩看）

检查对象：`/var/minis/workspace/OpenMinis-Desktop` @ `0689f3c`（v0.4.3）
检查范围：**只看方向对不对**，不做逐文件审计。
前提：**故意无视** NOTICE 偏离表 / `src/` 原则上不改 / `# PORT-FIX:` 三件套 —— 那套规矩是上一个模型给自己定的作业规范，不是架构目标，这里不作为约束。

---

## 总评

**骨架是对的。** 三条决定性的判断都做对了：

1. **内核只当依赖用，不当宿主** —— 业务逻辑全在 `src/openminis`，壳子（`desktop/` 4k 行 Python + `web/desktop/` ~7k 行手写 JS/CSS）只负责"开窗口、起服务、渲染"。
2. **壳与内核的接口是标准 HTTP + WebSocket**，和手机端跑的是**同一套 API**。这意味着壳不用理解内核，内核升级不用改壳 —— 这正是将来能持续更新的前提。
3. **用户数据在安装目录之外**（`~\openminis`，`desktop/paths.py` 的 `data_root()` 明确复用了内核自己的解析）。装到哪、更新成什么样，都不动用户数据。

"做成安装式 + 可更新"这条路是通的。真正要处理的是下面几件，按重要性排。

---

## 1【高】本地服务没有安全边界，而它背后是能执行 shell 的 agent

**现象（已逐条核实，不是推测）**

| 项 | 位置 | 事实 |
|---|---|---|
| 访问闸门 | `server/main.py:216 _access_gate` | `locked` 的第一项就是 `access_auth.has_password()`；**没设过密码 → 完全不拦**（默认状态） |
| CORS | `server/main.py:187` | `allow_origins=["*"]` + `allow_credentials=True` + `allow_methods=["*"]` |
| Starlette 行为 | `starlette/middleware/cors.py:163,176` | 在 `allow_all_origins + allow_credentials` 下，**把请求的 Origin 原样回显**并附 `Allow-Credentials: true` |
| 来源校验 | 全 `src/openminis/server/` | 除了上面那个 CORS 中间件，**没有任何** Origin / Host / Referer 校验 |
| WS | `server/main.py:794` | 同一把闸门；同样只看密码，不看 Origin |

**后果**：用户访问的**任意网页**都能跨域读写 `http://127.0.0.1:8799`。

- 读：`GET /api/chats/sessions`、`/sessions/{id}/messages` —— 全部会话内容。
- 写：`PUT /api/settings`（改服务商/模型配置）、`POST /api/sessions`。
- **最直接的一条**：`ws://127.0.0.1:8799/ws` —— WebSocket 不受同源策略约束，浏览器不挡跨站握手，而服务端也不校验 Origin。开一条 WS、发一帧 `{"type":"chat"}`，就是**一次 agent 回合**，而这个 agent 手里有 `shell_execute`。

**为什么这是"架构"问题而不是"漏了个参数"**：内核原本是给手机端用的 —— 那时候唯一的客户端是 App 自己的 WebView，服务绑在 loopback 上，**loopback ≈ 只有自己**。桌面壳把同一个服务放到了**用户自己的电脑**上，那里同时住着浏览器、别的程序、以及用户访问的每一个网站。**部署形态变了，威胁模型没跟着变。**

顺带把两个"看起来像补救、其实不算"的东西说清楚：让用户在界面上设"进入密码"是把安全责任推给用户，桌面端不该这样；而"绑 127.0.0.1"挡得住局域网，挡不住浏览器。

**方向（改动很小，且不用碰 `src/`）**

壳里发一个**每次启动随机生成**的 token，通过 query 参数交给 WebView（端口和 token 都是壳自己定的，WebView 天然知道）；在 `ui_mount.attach()` 里加一层中间件校验它 —— Starlette 的 `add_middleware` 是**头插**，`attach()` 在内核之后加，天然排在内核 CORS 之前，可以先拒后放。同时校验 `Host` 头（防 DNS rebinding）。再给 CORS 收成"只允许自己的 loopback origin"。

这一条建议排在所有事情前面：**它决定的是"敢不敢装到别人电脑上"**，而用户说的下一步正好是安装式。

## 2【高】打包形态选错了一半 —— 这正是"一键更新做不下去"的根因

用户的原话是「裸 exe 好像没办法一键自动更新」。实际情况比这更具体：

- 现在**同时发两种形态**：`OpenMinisDesktop.exe`（onefile，37.3MB）+ `OpenMinisDesktop-portable.zip`。
  onefile 每次启动都要把 ~37MB **解包到 `%TEMP%`**，退出再删 —— 启动慢、被杀软反复扫、且每次一个全新哈希。安装式场景**只该有 onedir**。
- 更关键的是**更新粒度**：PyInstaller 把纯 Python 编进了 exe 内部的 PYZ 归档，所以**改一行内核代码或一个前端文件，也只能重发整个 37MB**。
  可是这 37MB 里，天天变的是 `web/desktop`（几百 KB）+ `src/openminis`（Python 源码，几 MB）；而占大头的**解释器 + 依赖（~30MB）基本不动**。

**方向：把"运行时"和"载荷"分开。**

```
OpenMinis/
  OpenMinisDesktop.exe        # 引导器（很少变）
  _internal/                  # 解释器 + 依赖（很少变，~30MB）
  payload/openminis/          # ← 内核，启动时加进 sys.path
  payload/web/desktop/        # ← 界面
```

好消息是**仓库里已经在往这个方向走了**：`desktop/paths.py` 的 `desktop_web_dir()` 就是**优先取 `app_root()/web/desktop`，再退到 bundle 里**的。把同一套 overlay 逻辑扩展到内核（`sys.path` 里把 `payload/` 排在 bundle 前面），更新就变成"下一个几 MB 的包、覆盖目录、重启"。

**安装器相关的三件具体事**：

1. **形态**：Inno Setup 或 NSIS，**按用户安装到 `%LOCALAPPDATA%`**（不触发 UAC）—— 升级不需要提权，是"一键更新"能成立的前提。别做成 per-machine。
2. **WebView2**：目前对它是"假设已存在"。老一点的 Win10 上没有，装完就是白屏。安装器要带 WebView2 Evergreen 的引导（检测 → 缺失则装）。
3. **代码签名**：没签名 + **每次更新换一个新 exe** = **每次更新都吃一次 SmartScreen 拦截**。用户得学会点"仍要运行"——那就不叫一键更新了。要么把证书算进预算，要么明确接受这个体验并写进说明。

## 3【中】两个前端并存，成本在持续累积

`web/src`（上游 Vite 手机版）+ `web/desktop`（手写、无构建）。v0.4.0 的「补齐 6 个设置面板」就是这个模式的产物：**内核每有一个能力，桌面端就要有人手写一个面板**。

方向没错（手机版布局在桌面上确实不合适，而且暗色/触控假设都不同），但要**给桌面端定个边界**：

- 桌面 UI 只做内核 API 的**消费者**，不复制业务逻辑；
- 桌面端只做**薄壳**：对话 + 文件 + 必要的设置入口。别追着内核的功能清单跑 —— 那是一条没有尽头、而且会随上游漂移的跑步机；
- 真需要完整功能的用户，`--upstream-ui` 那条路留着（现在也是这么设计的）。

---

## 4【中】`app.js` 4057 行单文件 + 前端零测试 —— 已知 bug 全在这里

最近三轮修的 bug —— 流式正文重复、重开后工具卡堆底、生图引用丢失 —— **全部**落在 `web/desktop/app.js`，**没有一个**被自动测试发现（`tests/` 与 `web/scripts/` 里 grep 不到 `appendDelta` / `renderMessages`）。

方向（**保留"无构建步骤"这个优点**，它是这个项目真实的长处：改一个文件、重启、就生效）：

1. 用**原生 ES module** 把它拆开 —— 浏览器直接支持，不需要打包器。仓库里 `icons.js` 已经是 module 了，路已经铺好。
2. 把这轮审核子 agent 写的 **DOM harness** 落成仓库内的 node 测试（抽函数 + 假 DOM + 异步 rAF 队列）。这是唯一能防住这一类 bug 的办法。
3. **不建议**引入打包器 / 框架 —— 那会把"免工具链"的部署优势和"改完即生效"的开发体验一起丢掉，换来的收益在这个规模上不划算。

---

## 5【中】vendored 内核没有回流路径

`src/openminis` 是上游 PythonOpenMinis 的拷贝，NOTICE 记着 18 处偏离（**只增不减**）。而 `git remote -v` 里**只有自己的仓库**，没有 upstream，文档里也没有固定的同步流程 —— 意思是**上游的修复拿不进来，除非手工下 tarball 对着 diff**。

短期没感觉，中期是维护悬崖：内核 5.4 万行，自己修不动；偏离越多，将来一次性同步越贵。

方向：
1. 给上游配 remote（或至少把"基线是哪个 commit"写进 PORTING.md）；
2. **每处偏离都当成"对上游的潜在 patch"来养** —— 现在这套 `# PORT-FIX:` 标记其实就是在做这件事，缺的是"定期往上游提"这另一半。像 guard 的正则误判、Windows 路径语义，那些是上游的真 bug，提上去对所有人都有好处，也能把自己的 diff 减下来。

---

## 6【低】单实例保护是按端口判的

`server_runner.is_port_listening()` 当单实例锁，但端口是**可配的**、而且被占时会**自动换一个**。于是"另一个实例正在跑"和"端口恰好被别人占着"这两件事分不开；用户改过端口后，两个实例可以在**同一份数据目录**（同一个 SQLite、同一批会话文件）上并发跑。

方向：换成按数据目录的锁文件 / Windows 命名互斥体。

---

## 7【低】内核跑在壳的 daemon 线程里

一个进程、两个身份，好处是简单、端口天然可知。代价是内核崩了窗口跟着没，也没有 supervisor —— "窗口闪退"这类现场最难查（v0.3.5 已经踩过一次）。

方向：可接受，不必改。但**内核的未捕获异常必须被壳记下来**（这台机器上已经有一整套 `startup_trace`，继续用它就行）。

---

## 建议的推进顺序

| 顺序 | 做什么 | 为什么排这儿 |
|---|---|---|
| 1 | 本地服务加 token + Origin/Host 校验（上面第 1 条） | 决定"敢不敢装到别人电脑上"，而下一步就是安装式 |
| 2 | 只发 onedir + 把内核/界面拆成可覆盖的 payload 目录 | 没有这个，更新永远只能是"重下 37MB" |
| 3 | 安装器（per-user）+ WebView2 引导 + 签名决策 | 装了才能叫"安装式"，签名决定更新体验 |
| 4 | 前端拆 module + 补 DOM 测试 | 已知 bug 全在这，且现在是零防线 |
| 5 | 给上游配 remote、开始回流 patch | 不急，但越晚越贵 |

第 3 条里的**签名**是唯一一个需要用户花钱的决策，建议早点想清楚：它直接决定"一键更新"这四个字能不能兑现。
